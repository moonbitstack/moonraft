Porting notes

41 scripts,
replayed block by block

This library is a MoonBit port of etcd-io/raft pinned at commit 26647d5. The reference tree ships 41 scripted scenarios; they are archived verbatim, replayed through the same RawNode, Changer and quorum code the library ships, and their expected output is compared byte for byte. This page records how that works and what it took to converge.

The corpus

Archived as they are, embedded at build time

The reference tree's datadriven scripts — the testdata/*.txt corpus — are copied without edits into scripts/testdata/etcd/, and scripts/gen_dd_scripts.py embeds them into src/core/dd_scripts_wbtest.mbt so the replay needs no file IO and runs on every target.

The comparison

A byte comparison, not a shape check

The harness executes every command the reference understands and renders its output in the reference's own format — a port of util.go's DescribeReady / DescribeMessage / DescribeEntry family. A script's expected block is then compared as text, so whitespace, field order and formatting all count.

confchange and quorum — 13 scripts

Compared case by case; all 13 reproduce the reference exactly, asserted by datadriven: quorum and confchange scripts reproduce upstream exactly.

raft — 28 scripts, 558 cases

Scored block by block by datadriven: raft scripts reproduce upstream block by block: all 558 cases match. The scoreboard asserts the exact count, so a change that stops one script reproducing is a failure rather than a lower score.

Convergence

What closed the last of the gap

In the order each was found and fixed, each with a test that fails before it.

The durable log, and the append thread

raft-log prints the durable log, not the unstable tail, and the append thread persists what it was handed before the acknowledgement is delivered. That is what makes the ABA-race script's interleaving visible at all: a stale append from an older term still lands, and the storage acknowledgement then reports the ignored stabilisation instead of silently doing nothing.

A local compaction is not an installed snapshot

Both move the core's snapshot index, but only an install produces Ready.snapshot — so a compacted leader no longer hands its own application a snapshot of its own log.

A committed change applies before the durability responses

The caller applies CommittedEntries and then calls Advance. That ordering is what makes the leader probe a newly added peer with the pre-advance commit index.

The leader's own progress comes from the tracker

Not synthesised from the log tail, so a proposal does not count as replicated before its self-acknowledgement is durable.

A forwarded proposal keeps its unset 0/0

Only appendEntry stamps a term and an index on it, and a response from a peer the node no longer tracks is refused with raft: cannot step as peer not found.

The leave-joint entry is broadcast at once

The automatic leave-joint entry goes out in the same turn it is appended, matching what proposing a configuration change does.
